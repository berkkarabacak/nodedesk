05. DOMAIN DEFINITIONS: NEVER MIX THESE CONCEPTS
==========================================================================

Account: a backend-verified Google identity, keyed by provider issuer/subject,
not merely by display name or email text.

Local device: the machine currently running this NodeDesk instance, identified
by persistent cryptographic/device identity. IP address changes do not change it.

Public Device ID: proposed nine-digit human-readable lookup identifier displayed
as three groups of three digits. Use server-side allocation/collision handling,
preserve leading zeroes, rate-limit resolution, and do not treat it as a secret.
Keep internal stable identity separate from this public lookup value.

Enrollment: the owner explicitly associates the local device with an account.
Account switching must not silently transfer device ownership.

Saved computer: an account address-book entry pointing at a stable device.
Owner devices appear after enrollment; approved shared devices can be saved.
Saving a reference does not grant access.

Discovery: finding a device's reachable network endpoint on LAN/tailnet/another
verified route. A discovered device is not automatically saved or trusted.

Trusted controller: a specific device identity the host has authorized. Trust
is stored/enforced on the host; removing credentials only on the controller is
not equivalent to revoking that controller on the host.

Unattended access: host policy allowing already trusted owner controllers to
connect without a person pressing Accept. Off by default.

Attended access: a host-side person explicitly accepts a pending request and
its permission set. Trust is not automatically created by Accept.

Session: one authenticated remote-desktop connection, with its own ID, verified
target, effective permissions, lifecycle, and timestamps.

Transfer: one queued file operation, identified independently of its filename,
with source/target device IDs, direction, total/acknowledged bytes, and state.

Address-book removal: delete the saved entry from the active account on all its
controllers. It does not uninstall NodeDesk, unclaim an owned host, or revoke
every controller. Clearly describe that scope in the confirmation.
Proposed rule: removing an enrolled owner device hides it using an account-level
tombstone until explicitly added again; background enrollment sync must not
immediately recreate the row. Retain ownership and host controls separately.

Trust revocation: remove one controller's host-side authorization, reject future
attempts, and terminate any active session/transfer authorized by that grant.
These are separate operations with separate UI wording and tests.

Proposed initial defaults:
- Hosting remains off until the owner explicitly enables it.
- Unattended access off.
- New incoming request: screen viewing required for a desktop session; control,
  files, and clipboard available to approve; audio off initially, matching the
  permission mockup. Effective access is exactly what the host accepts.
- Stay signed in on, visible and changeable before Google sign-in.
- Quality Auto; preserve explicit settings from existing installations.
- Light theme for new installations; preserve existing explicit preference.
- One outgoing desktop session at a time in this release; do not silently kill
  a running session when the user clicks another computer.
- One incoming desktop session at a time; report Busy for a second request.
- Transfers queued serially initially; independent transfer IDs and cancel
  actions still required. Parallel transfer support is not necessary.

Proposed engineering test constants (centralize/configure them):
- Incoming approval expiry: 30 seconds from host-issued request deadline.
- Host presence stale after 30 seconds without a verified heartbeat/update.
- Connect attempt timeout: 30 seconds, except visible host approval waiting.
- Reconnect: up to 3 attempts with delays of 1, 2, and 4 seconds; stop earlier
  for denied/revoked access, disabled hosting, cancellation, or sign-out.
These are requested product behaviors, not measured timings from the repository.
Use fake clocks in tests. Do not hard-code countdowns independently in screens.

06. USER JOURNEYS: IMPLEMENT THE WHOLE EXPERIENCE
==========================================================================

J1. FIRST-TIME OWNER SETUP AND FIRST SESSION
User goal: remotely use my Windows Home PC from another computer.
1. Install/open NodeDesk on the host. See Login with a clear Google action.
2. Complete Google sign-in in the system browser and return to NodeDesk.
3. Enroll the local device only after explicit owner consent.
4. Open This Computer, check its name/Device ID, and enable remote access.
5. Complete required host setup with visible progress and OS consent as needed.
6. Leave unattended access off unless intentionally enabling it.
7. Install/open NodeDesk on the controller and sign into the same account.
8. See the enrolled host in My Computers once directory sync succeeds.
9. Click Connect. If this controller is new, receive a real request on the host.
10. Accept the controller with selected permissions, and separately authorize
    persistent trust if requested. Establish underlying streaming pairing safely.
11. See real remote video and use input only if control was granted.
12. Disconnect and return to the same My Computers list.
Success: a real two-computer session, with no manual IP/codec/port setup on a
supported route. If network reachability/setup is missing, explain it honestly.

J2. RETURNING OWNER: THE ONE-CLICK EXPERIENCE
Preconditions: host reachable, hosting enabled, controller already authorized,
unattended access on, account session valid.
1. Open NodeDesk; restore sign-in safely.
2. Load saved computers and current status.
3. Click the remote computer's Connect action exactly once.
4. Show connection progress, then its actual desktop.
5. Work, optionally transfer a file, then Disconnect.
Success: no repeated authentication dialog, pairing PIN, typed ID, or detail-page
detour. One click starts the process; it does not promise zero network latency.

J3. SAME ACCOUNT ON A BRAND-NEW CONTROLLER
1. Sign in on a new laptop using the owner's Google account.
2. See the existing saved list without importing files or typing host IDs.
3. Click a host. The host confirms/authorizes this new controller once.
4. After trust is established and unattended access enabled, later connections
   follow J2. An attacker with a guessed Device ID cannot follow this journey.

J4. HELP SOMEONE ELSE WITH THEIR COMPUTER
1. The host enables remote access and shares its public Device ID.
2. The helper opens Add computer, enters a name and the ID, then submits.
3. Resolve the target through the actual directory. Save a reference only when
   allowed; display pending authorization distinctly from trusted access.
4. Connect sends the host a request with the helper's verified account/device.
5. The host selects permitted actions and presses Accept or Reject.
6. Accept opens only that session's granted capabilities; Reject/expiry ends it.
7. On the next helper session, approval is required again in this release.
Success: the owner controls access. The helper is not silently trusted forever.

J5. SEND AND RECEIVE FILES
1. Open File Transfer or Files in an active session.
2. Choose a reachable, authorized target. Show direction explicitly.
3. Send: browse/drop actual local files; receive: browse authorized remote files.
4. Queue each operation with a unique transfer ID and real progress.
5. If interrupted, offer Retry and resume only after checking file identity.
6. Show Done only after destination confirmation; offer Open folder for downloads.
Success: actual bytes arrive intact at the intended device, never at a newly
selected target due to an asynchronous race.

J6. NETWORK INTERRUPTION AND RECOVERY
1. During an active session, connectivity is lost.
2. Freeze/cover stale frames, disable remote input, and show Reconnecting.
3. Attempt bounded recovery to the same verified device/session context.
4. If permissions are still valid and recovery succeeds, resume the session.
5. Otherwise show a useful failure with Retry and Back to My Computers.
Success: no phantom Connected status, runaway retry loop, or stale input replay.

J7. HOST DISABLES OR REVOKES ACCESS
1. Owner turns remote access off or removes a trusted controller in Settings.
2. Native host enforcement updates immediately, including existing paired paths.
3. Active affected sessions/transfers terminate and pending requests are invalidated.
4. The affected controller receives an accurate message and cannot auto-reconnect.
Success: the switch and revocation change real access, not just a label.

J8. SIGN OUT OR SWITCH GOOGLE ACCOUNT
1. Choose Sign out or Switch account from Settings.
2. If work is active, explain affected sessions/transfers and allow cancellation.
3. On confirmation, stop account-authorized work and clear account credentials
   and in-memory private data for this controller context.
4. Reject late callbacks/events from the old account.
5. Sign in as the new account and show only its saved list and authorization.
6. Do not transfer ownership of This Computer or expose the old account's data.
Success: two accounts cannot see or operate each other's device lists by accident.

J9. CHANGE SETTINGS AND RETURN LATER
1. Choose theme, default quality, startup, and sign-in persistence.
2. Save each change with visible pending/success/failure behavior.
3. Theme changes immediately across app-owned surfaces.
4. Default quality affects new sessions; in-session quality is session-specific.
5. Restart the app and verify retained preferences and valid account restoration.
Success: visible switches reflect actual persisted or native-applied settings.

07. REQUIRED STATE MODELS
==========================================================================

Keep account, host, session, and transfer state independent. Do not reuse one
global loading/connected/error boolean for unrelated asynchronous operations.

Authentication:
restoring -> signedOut | signedIn | restoreError
signedOut -> signingIn -> signedIn | signedOut | authError
signedIn -> refreshing -> signedIn | reauthenticationRequired
signedIn -> signingOut -> signedOut
Every asynchronous response is associated with an account-generation/request ID.

Saved-computer list:
loading -> loaded | empty | loadError
loaded -> refreshing -> loaded | staleWithError
Search yields noMatches, which is different from no saved computers.
Directory freshness and route reachability are separate facts.

Host:
disabled -> enabling -> ready | setupError
ready -> disabling -> disabled
Unsupported platform/capability is explicit, not an endless enabling state.
Effective unattended access = hosting enabled AND saved unattended policy AND
valid trusted-controller authorization. One shared policy powers both switches.

Connection:
idle -> resolving -> authorizing -> awaitingApproval (if needed) -> connecting
-> connected -> reconnecting -> connected | failed
Any pending state -> cancelling -> cancelled.
connected -> disconnecting -> disconnected.
Access denied/expired/revoked is terminal for that attempt; retries need a new
explicitly valid request/grant. Approval expiry is separate from connection time.

Transfers:
queued -> preparing -> transferring -> verifying -> completed
transferring -> interrupted -> retrying -> transferring | failed
queued/preparing/transferring/interrupted -> cancelling -> cancelled.
Record account ID, session/grant ID, transfer ID, source/target IDs, destination,
file identity, acknowledged bytes, and last error. Do not correlate by name alone.

Important implementation rules:
- Await native mutation outcomes; do not immediately navigate away and pretend
  success. On failure restore a truthful state and keep a retryable error.
- Subscribe before starting operations that emit events.
- Dispose listeners, abort requests where possible, and reject late events using
  IDs/epochs, including callbacks after unmount and account switching.
- Cancellation is enforced by the native/backend operation, not only the UI.
- Connect errors must not mark a device permanently offline without evidence.
- When the route's address changes, retain device identity and authorization.

  setup requirements honestly if that is the initial route.
- Do not label account synchronization as anywhere connectivity.
- A no-extra-network-setup internet mode needs separate signaling, NAT traversal,
  and/or relay implementation. Evaluate compatibility with Sunshine/Moonlight;
  do not casually assume WebRTC/TURN transports their existing protocol.
- Track automatic internet connectivity as a distinct milestone and do not
  claim TeamViewer-like anywhere behavior until different-network testing passes.
- Do not automatically configure public port forwarding or weaken TLS checks.

Compatibility:
- Migrate persisted settings additively. Missing new fields get safe defaults.
- Preserve old local hosts, codes in OS keychain, and working pairing where safe.
- Do not infer new account/device trust from an old display name or IP address.
- Give migrated devices an explicit claim/authorization step if needed.
- Keep legacy LAN use reachable under a secondary local/advanced mode; this is a
  proposed compatibility path, not a reason to omit the required Google journey.
- Local mode must not inherit cloud-account permissions after sign-out.

14. COMMON IMPLEMENTATION MISTAKES TO AVOID
==========================================================================

- Rebuilding the landing website instead of apps/desktop.
- Treating support.js/DCLogic mockup scripts as the production application.
- Implementing only attractive screens without native/account behavior.
- Using example Mira/Daniel profiles, nine-digit IDs, latency, or file progress
  as real data in the packaged app.
- Treating auth.rs as a Google sign-in implementation.
- Relabeling IP address or shared access code as public Device ID.
- Inferring trust from same account, discovery, saved-list membership, or ID.
- Marking Connected immediately after spawning Moonlight.
- Showing a toolbar in React that is inaccessible behind the actual viewer.
- Applying permission toggles only to button visibility.
- Revoking local stored credentials while leaving host authorization valid.
- Treating HMAC as encryption or logging secrets to debug account integration.
- Automatically trusting a helper forever after one Accept.
- Keeping separate unattended/Stay signed in states that contradict one another.
- Completing history/transfer rows based on UI timers rather than verified results.
- Resuming any same-size/name file without verifying content identity.
- Sharing a single global transfer cancel flag across independent queue entries.
- Letting late auth/session/transfer events mutate a different account or target.
- Silently killing another stream by overwriting the active child-process handle.
- Stating internet access works when only directory sync or LAN discovery works.
- Advertising folder transfer, live quality, monitors, or clipboard/audio control
  while those functions exist only in browser preview.
- Guaranteeing pre-login/UAC/lock-screen control without capability testing.
- Adding premium plans, enterprise dashboards, chat, AI assistants, teams/billing,
  or unrelated features before the specified core journey is proven.
- Removing advanced working features merely to copy the simple mockup.
- Declaring PASS for tests not run, screenshots alone, or README aspirations.
